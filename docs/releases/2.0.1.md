# IAGA Sentinel 2.0.1 — Layers That Reported Themselves Present and Were Not

Released from `main`. Full entry: [`CHANGELOG.md`](../../CHANGELOG.md).

## What this release is

A patch release with no feature in it. Every entry predates 2.0.0, and most
predate every release: they were found by an audit that ran the product rather
than reading it, and by exercising the surfaces the release benchmarks never
touched — the CLI, the MCP proxy, the kernel adapter, the SDKs.

The theme is uncomfortable and worth stating plainly. Four of these are
components that **announce themselves** — in the API response, in the layer
inventory, in the config schema — and do nothing:

| Component | What it claimed | What it did |
|---|---|---|
| Rate limiter | enforcing 60/min | allowed 80 of 80 calls, for the first hour of host uptime |
| Containment (layer 5) | present in the pipeline | produced a result 0 times out of 42 actions |
| `AgentProfile.toolTrust` | parsed, validated, echoed back by the API | discarded by both storage backends; every agent scored at 0.7 |
| `RateLimiter::cleanup()` | prunes the window map | had no caller anywhere in the tree |
| `GET /v1/rate-limit/status/{agent}` | the agent's current traffic | read a key nothing writes; reported 0 under any load |

That last row was found **after** the others, by driving a finished 2.0.1 build the way an
operator would rather than by reading the diff again: 12 governed calls, status still
`requestsLastMinute: 0`, and the very next call refused. Fixing the window defect had
exposed a second, independent one underneath it.

A gate that reports itself present and never fires is worse than one that is
absent, because the absence is at least visible.

Three more are the same shape one level up — a refusal reported as success:
`iaga proxy` wedged on the mandatory MCP handshake notification, `iaga run`
exited 0 when the kernel refused the launch, `iaga replay --export` wrote
authentic-looking but empty evidence and exited 0. In each case the library
underneath was correct **and covered by a test**; the thin adapter on top was
neither, so the suite stayed green over all three. And the TypeScript SDK
followed HTTP redirects, so a `307` from the sidecar URL to an attacker's server
returned that server's `allow` with no evidence written anywhere.

## Compatibility

The receipt schema, the wire contract and the Dictum language are **unchanged**.
No receipt field was added, removed or renamed, so every verifier and the receipt
database schema are untouched, and receipts produced by any earlier release still
verify.

Four changes are observable to a caller, all deliberate and all the point of the
release:

1. **The rate limiter now refuses.** If you run on a host that reboots often, or
   in short-lived containers, you were effectively running without one.
2. **`sandboxResult` now appears** on high-risk actions in `/v1/inspect`
   responses. It is advisory: not in the signed receipt, and no term of the
   composite score.
3. **Three CLI paths now exit non-zero on a refusal** (`iaga run` 1/2,
   `iaga replay --export` 3) instead of 0. Shell scripts using `&&` after them
   will now stop where they previously continued — which is the fix.
4. **A profile that explicitly sets `toolTrust`** is now scored with the value it
   declares rather than 0.7, so that agent's `risk_score` can move. A profile
   that does not set it is unaffected.

## Upgrading

1. Take a backup. Migration `0006_tool_trust` is **one-way in practice**: a 2.0.0
   binary meeting a 2.0.1 database refuses to start, because sqlx validates the
   applied set before applying anything and this repo never calls
   `set_ignore_missing`. `scripts/rollback_0006.{sqlite,postgres}.sql` undo it;
   read the header of the SQLite one before you need it.
2. `iaga migrate --db <url>` (or just start `serve`; migrations run at boot).
3. Nothing else. There is no new configuration key, no new endpoint, and no
   policy change required.

The migration adds the column with a default of `0.7` — the value those rows were
already being scored with — so an upgraded database governs exactly as it did
before, and no signed byte moves for a profile that never set the field.

## If you deploy with Helm or kustomize

Check your image tag. Through 2.0.0 the chart labelled every object with the
product version and then pulled `ghcr.io/edoardobambini/iaga-sentinel:v1.8.1` —
three releases old, from a namespace CI stopped publishing to at 1.9.0. Both
paths now point at `ghcr.io/iaga-team/iaga-sentinel:v2.0.1`. See
[`charts/iaga-sentinel/README.md`](../../charts/iaga-sentinel/README.md) for the
three places the tag is pinned and how to check they agree.

## Release artifacts

Tagging now builds four targets — Linux x86_64, macOS x86_64 and aarch64,
Windows x86_64 — and publishes `iaga-<version>-<target>.tar.gz` plus a single
`SHA256SUMS`. Each archive carries **both** binaries, `iaga` and `iaga-verify`,
with `LICENSE`, `DISCLAIMER.md` and `THIRD_PARTY_NOTICES.md`. The previous
release job attached one bare Linux `iaga-sentinel` binary with no checksum and
no verifier, which meant the offline proof the README sells was not in the
release.

**No prebuilt arm64 Linux binary, and the reason is worth stating.** `reqwest`'s
default features pull `hyper-tls → native-tls → openssl-sys`, which links the
system OpenSSL on Linux; cross-compiling that needs an arm64 OpenSSL *sysroot* on
the build runner, not just a cross linker. The first v2.0.1 build attempt failed
exactly there. The honest fix is to stop linking OpenSSL at all — `reqwest` with
`default-features = false` and `rustls-tls`, which is already in the lock file —
but that changes the TLS trust store of the shipped binary, and a patch release
is the wrong place to change how the product validates certificates without
testing it against a proxy-terminated network. Tracked for 2.1.0. Until then,
arm64 Linux builds from source:

```sh
cargo install --git https://github.com/IAGA-TEAM/IAGA-Sentinel --tag v2.0.1 --locked \
  iaga-sentinel-core iaga-sentinel-verify
```

## Known gaps, stated rather than glossed

- **The Postgres *receipt* store is still untested at runtime.** The core schema
  path is not: `0006` was applied to a live Postgres 16, the column and the
  `_sqlx_migrations` row were read back with `psql`, a profile carrying
  `toolTrust: 0.05` round-tripped through import → column → `GET /v1/profiles`,
  a governed `/v1/inspect` blocked and wrote its audit row, and
  `scripts/rollback_0006.postgres.sql` was executed: it printed the value it was
  about to discard, dropped the column, deleted the ledger row, and a subsequent
  `iaga migrate` re-applied cleanly with `tool_trust` back at the `0.7` default —
  the documented data loss, observed rather than asserted. What remains
  unexercised on Postgres is `iaga-sentinel-receipts`, which needs
  `IAGA_SENTINEL_TEST_PG_URL` set (see `CONTRIBUTING.md`).
- **`SessionDAG.block_count` still counts only FSA denials**, so the 3-strike
  session ceiling is not reachable from the layers that do most of the refusing.
  Documented in-code, unchanged here: feeding it the pipeline count would latch
  sessions that do not latch today, which changes verdicts and moves signed bytes.
- **Session state is process-global**, keyed by `sessionId` with a fallback to
  `agent_id`, so two workspaces sharing a process and a session key share the
  accumulated taint labels.
- **`tract-nnef` keeps RUSTSEC-2026-0217** (6.1, `--features ml` only, in no
  shipped artifact). Upgrading it forces `time` down into RUSTSEC-2026-0009
  (6.8 — worse), and the constraints cannot both be satisfied inside
  `tract-onnx = "0.21"`. Recorded as a trade-off rather than committed as a
  net-worse lock file.

## Verifying a receipt offline

Unchanged, and the point of the product:

```sh
iaga replay <run_id> --export chain.json
iaga-verify chain.json            # -> CHAIN OK
```

No server, no database, no network. A chain exported by any release from 1.3.0
onward still verifies with the 2.0.1 verifier, and vice versa.

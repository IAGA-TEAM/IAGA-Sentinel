# IAGA Sentinel 2.0.2 — The Thresholds Postgres Never Read

Released from `main`. Full entry: [`CHANGELOG.md`](../../CHANGELOG.md).

## What this release is

Follow-up hardening after a live 76-request attack-suite case study, and then a
release verification that ran the whole thing again from the outside.

The theme is a backend that reported itself configured and was not. Postgres
decoded its own `INTEGER` threshold columns as `i64`; sqlx rejects that, and the
fallback happened to be the same number as the default, so **every Postgres
workspace was governed at 70/35 no matter what its policy said** and nothing
anywhere said so. It reads back correctly now, which means a Postgres deployment
that ever configured custom thresholds will see its verdicts change. That is the
point of the fix and it is still a change in what the product blocks, so it is
called out first here and first in the compatibility list.

The rest closes the two attacks that got through the case study, gives the layers
that changed the tests they never had, and corrects a set of published claims —
including several this same change set introduced while it was being written.

## Compatibility

**The signed receipt wire format is unchanged and existing chains verify
byte-for-byte.** Measured rather than asserted: a chain generated by the 2.0.1
binary verifies with the 2.0.2 `iaga-verify`, a chain generated by 2.0.2 verifies
with the 2.0.1 verifier, and `auditEvent.reasons` is identical in content and
order for identical traffic.

What does change for a consumer, in order of weight:

1. **Postgres verdicts move**, as above. `riskScore` on `/v1/audit` and
   `/v1/reviews` also stops reading back as `0`, and `policyHash` on **new**
   receipts changes for any Postgres workspace whose thresholds were not the
   defaults. SQLite is unaffected.
2. `/v1/inspect` gains `layerRoles` (always present) and
   `taintAnalysis.correlationScope`.
3. `risk.reasons` — and the review queue — carry the Dictum and cost-control
   attributions, so a consumer counting or exact-matching that array sees more
   lines.
4. `POST /v1/sandbox/{id}/approve` and `/reject` are admin-only: an
   `agent`-scoped key that got `200` now gets `403 admin_scope_required`.
5. `audit_events.created_at` is the pipeline's decision time, so the audit read
   order changes for rows written inside the same second.
6. `GET /v1/cost/over-time?bucket=day` on SQLite returns the RFC3339 form,
   matching Postgres.
7. The MCP `tools/list` text for `http.fetch` changed, and its schema accepts
   seven destination key names where it demanded `destination`.
8. `iaga validate` and `iaga import` print policy lint output. Exit codes
   unchanged; on the configs in this repo that is one
   `warning [medium] incomplete_coverage`.
9. The Python `@governed` decorator stops sending `ctx`/`context`, and the Helm
   chart's `image.tag` no longer has a default.

## Upgrading

Migration `0007_audit_read_path_indexes` adds two composite indexes on
`audit_events` and drops nothing; both statements are `IF NOT EXISTS`. A normal
rolling upgrade, with none of the ceremony `0006` needed.

Verified on both backends: a database created by the 2.0.1 binary, then started
under 2.0.2, comes up with `_sqlx_migrations` running 1→7, its rows intact and
the API answering.

The reverse direction follows the usual sqlx rule — a 2.0.1 binary meeting a
2.0.2 schema refuses to start, because the migrator validates the applied set
before applying anything and this repo never calls `set_ignore_missing`.

## If you deploy with Helm or kustomize

**`image.tag` no longer has a default and `helm install` will refuse without
it.** That is deliberate: it used to default to the product version and render a
valid-looking reference to `ghcr.io/iaga-team/iaga-sentinel`, which does not
exist, so the first sign of trouble was a pod in `ImagePullBackOff`. The render
now fails with a message naming the value and what to set.

```sh
helm install sentinel ./charts/iaga-sentinel \
  --set image.repository=<your-registry>/iaga-sentinel \
  --set image.tag=<your-tag>
```

The chart's own version moves `0.1.0` → `0.2.0`, because requiring a value that
used to be defaulted is a breaking change for anyone who relied on it.

> **The published image still does not exist.** `ghcr.io/iaga-team/iaga-sentinel`
> does not resolve — the package is private and the tag push fails the manifest
> with HTTP 403. The last publicly published image remains
> `ghcr.io/edoardobambini/iaga-sentinel:v1.8.1`, six releases behind. Build your
> own from the shipped `Dockerfile`:
> `docker build -t iaga-sentinel:local .`

## Known gaps, stated rather than glossed

- **`POST /v1/nhi/challenge` persists nothing to Postgres.** `create_challenge`
  writes only the in-memory map and the durable `store_challenge` has no caller,
  so challenges do not survive a restart. Reported rather than silently changed:
  wiring durable challenges has restart semantics that belong in their own
  release.
- **Dictum cannot express "whichever destination key is present".** The MCP
  schema and the workspace egress layer accept seven key names; the shipped
  Dictum example reads `destination` only, and `url_host()` errors — fail-closed
  — on the other six. Cover alias key names with `destinationFields` on the
  workspace policy instead. A coalescing builtin is tracked separately.
- **`RUSTSEC-2026-0217`** (tract-nnef 0.21.12, integer overflow / OOB read on
  NNEF model load) is accepted in `.cargo/audit.toml` with its reasoning. It
  reaches the shipped binary only through the optional `ml` feature.
- **`iaga replay` reads SQLite only**, even when the receipt store is Postgres.

## Verifying a receipt offline

```sh
iaga replay <run_id> --export chain.json
iaga-verify chain.json                  # -> CHAIN OK
iaga-verify chain.json --expect-count 3 # -> also fails a tail-truncated chain
```

No server, no database, no network. A chain exported by any release from 1.3.0
onward still verifies with the 2.0.2 verifier, and vice versa.

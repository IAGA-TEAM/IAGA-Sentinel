# IAGA Sentinel 2.1.0 — Evidence That Says What Happened

Full entry: [`CHANGELOG.md`](../../CHANGELOG.md).

## What this release is

An audit of `2.0.2` across release and real-user paths, followed by adversarial passes whose only
job was to refute the findings. Findings are included here only when a reproducer survived that
challenge; exact suite counts below come from the code being released, not the earlier audit tree.

The theme is the one that matters most for a product whose deliverable is an evidence record:
**four separate ways that record could be wrong.** Not "an attack got through" — the governance
verdicts on `/v1/inspect` are identical to 2.0.2 across the 48 `/v1/inspect` cases of the
characterization corpus; see Compatibility below for exactly which other verdicts move. The
problem was the record itself: it could assert something that never happened, or be unavailable to
the people entitled to read it, or be forged by the very agent it was written about.

The heaviest single item is not a bypass at all. A payment amount of `10.50` in a request body,
sent to a public host, produced a **signed receipt carrying `EXFILTRATION DETECTED`**. The
internal-address check matched the substring `"10."` anywhere in the serialized payload, body
included. For an evidence product a signed false accusation is worse than a missed detection, and
it survived because nothing tested it.

Capability tokens also stop being decorative. Through 2.0.2 the product minted, signed, stored and
published — through a documented endpoint and an SDK method in both languages — a credential that
authorized nothing: the signature was never verified, the tokens lived in a process-global map that
a restart emptied, `revoke_token` had no route, and the issuing route had no admin guard, so any
agent-scoped key could mint `capabilities: ["*"]` for any agent.

## Compatibility

**The signed receipt wire format is unchanged and existing chains verify byte-for-byte.**

**Governance verdicts on `/v1/inspect` are not claimed identical to 2.0.2.** Several intended
changes make that impossible: an agent-scoped key may now submit only its bound `agentId`, the
prompt firewall's semantic stage actually runs, common Unicode/signature bypasses are closed, and
false positives on defensive prose and inert HTML are removed. Consumers that exact-match risk
scores or reasons must re-baseline.

The same-hour control remains necessary for every comparison. The adaptive scorer carries an
off-hours signal, so a corpus captured at 04:00 and one captured at 05:00 differs in
`adaptiveRisk.totalScore`, in the `"adaptive risk: score=N"` policy finding, and in `risk_score` on
a signed receipt. Comparing across that boundary invents a signed-score change.

Across the 342-case corpus there are exactly ten verdict changes, all on `/v1/response/scan`: the
`mongodb+srv://root:s3cr3t@cluster0.mongodb.net/db` cases. Nine passed 2.0.2 completely (`allow`,
risk 0) and one reached `review`/55 through the sensitive-pattern scan; all ten are now `block`/80,
because a connection string with an embedded password is a credential.

**That is a statement about the corpus, not about the product.** `/v1/inspect` moves too, and the
corpus could not have shown it: it holds no `maxDecision: block` policy, no credential-bearing URL
on the inspect path and no bare `10.` in a body. Measured directly against a 2.0.2 binary in the
same hour, an inspect payload carrying a connection string goes from risk 70 to 76 and gains an
`EXFILTRATION DETECTED` taint finding, and the `10.50` payment case goes from 76 to 70 and loses
its false one. `maxDecision: block` flips allow to block outright. If you depend on exact risk
scores, re-baseline against your own traffic.

Three user-path corrections have their own compatibility surface:

- One `iaga proxy` or `iaga mcp-doctor` process now gives all of its governance checks one run
  identity, using `<agent>:mcp-proxy-*` or `<agent>:mcp-doctor-*`; when N is nonzero they form one
  N-receipt run. Older one-receipt runs keep their original UUIDs.
- A bare `http` then `shell` sequence no longer creates a critical `reverse_shell_setup` match or
  blocks the whole session for 60 seconds. It still contributes the signed +25
  `network-delivered execution arc` anomaly. External responses remain subject to the per-request
  `EXTERNAL_TOOL → ShellExec` taint block; internal API responses (localhost, `127.*`, `10.*`,
  `192.168.*`, `*.internal`, `*.local`, `*.corp`) are not vetoed by that rule, matching the existing
  `file_read → shell` and `db_query → shell` exposure.
- Missing DLQ entries, webhooks, capability tokens, NHI challenge identities, sandbox entries,
  fingerprints, threat indicators, templates and session metrics now share the documented
  `404 not_found` error body. The template route changes from its old documented `400` to `404`.
  Unsupported audit export formats now return `400 invalid_request`; an omitted or empty format still means JSON.

**Migrations `0008` and `0009` are additive** on both backends: one new `capability_tokens` table
and one nullable `api_keys.agent_id` column. Migrations `0001`–`0007` are byte-identical to 2.0.2,
which is what keeps every existing database openable — sqlx compares a SHA-384 checksum per
version, and reusing a taken number is what left an earlier 2.1.0 tree unable to open any
already-migrated database.

Measured end to end, not asserted: a database created by the 2.0.2 binary (versions `1..7`) was
opened by this build, which ran it to `1..9`, added both objects and kept its rows intact. The
reverse is the usual sqlx rule and also measured — the 2.0.2 binary meeting a 2.1.0 database refuses
cleanly rather than corrupting anything:

```
Failed to initialize SQLite database: Storage error: Failed to run SQLite migrations:
migration 8 was previously applied but is missing in the resolved migrations
```

## Upgrading

The schema upgrade is automatic. Three operational checks are required:

1. **Rotate every `agent`-scoped API key.** New keys require an identity binding:
   `iaga gen-key --scope agent --agent-id <id>` or `agentId` in `POST /v1/auth/keys`. Existing
   admin keys stay valid; existing agent keys have a null binding and fail closed with
   `403 agent_key_unbound`. Finish the rollout before distributing replacements, because a
   still-running 2.0.2 process does not enforce the new column.

2. **If you drive the API with an `agent`-scoped key**, the read halves of the governance surface
   now require admin — see item 1 in the CHANGELOG for the full route list, which came out of
   enumerating every route/method pair against its guard rather than sampling. If an agent genuinely
   needs its own record, that is what the new `read:self` capability token is for; it covers profile,
   analytics, fingerprint and rate-limit state. The API key and capability token must name the same
   agent. The operator console is unaffected. A monitoring scraper pointed at
   `/v1/telemetry/*` now needs an admin key.
3. **If any workspace policy sets `maxDecision: block`**, that tool was being governed exactly as
   if it had said `allow`. It will now deny. Grep your policies before restarting.

## How this was verified

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and
  `cargo clippy -p iaga-sentinel-core --features postgres --all-targets -- -D warnings`.
- `cargo test --workspace`: **665 passing, 0 failing, 2 ignored**, up from 546 at 2.0.2. Both counts
  were taken by running the suite, the 546 in a worktree checked out at `b444886` rather than
  quoted. The two ignored are the live-sidecar `GovernedTool` cases; CI runs them with
  `-- --ignored` once its own sidecar is up. Also green against a live PostgreSQL 16: **477** with
  `-p iaga-sentinel-core --features postgres` and **46** with `-p iaga-sentinel-receipts --features
  postgres`. And **731** with `--workspace --all-features -j 2`.
- The `-j 2` is needed only for the all-features build, and only here: unconstrained on Windows it
  dies at link with `LNK1102` / `os error 1455` (the pagefile), having run **zero** tests. That is a
  property of the workstation, not a result. CI runs the same step on Ubuntu after reclaiming ~20 GB
  of preinstalled tooling.
- Each of the eight per-feature CI steps green on its own: `ml`, `plugins`, `dictum-wasm`,
  `plugins,plugin-attestation`, `otel-receipts`, `plugin-manifest-signing`, `cost-control`, and the
  `linux-bpf` scaffold build. Plus `cargo fmt --check` and both clippy invocations.
- **The Operator Console was rendered, not only fetched.** All 13 views driven through headless
  Chrome with JavaScript executed: every view activates, no console errors, no error banner, and the
  Decisions table lists the actions that had just been governed with their agent, tool, decision and
  risk. The 30 endpoints the console polls all answer `200`; SSE delivered every `action_governed`
  event live; the exported chain verified `CHAIN OK` against a **pinned** key from all three
  verifiers with byte-identical output.
- **What was not verified, said plainly.** CI has never run against this tree — every number above
  comes from one Windows workstation, and the first CI run happens on push. The shipped binaries are
  built at default features, so the `DATABASE_URL` redaction is covered by a unit test rather than a
  live PostgreSQL boot, and the chart's PostgreSQL install needs an image built with
  `--features postgres`; both are in Known gaps rather than glossed.
- Every security fix has a test that was **watched failing** against the pre-fix code, and the
  failure output was captured verbatim during this audit and is reported with the handoff rather
  than inferred from a later green run.
- The characterization corpus replayed against a real 2.0.2 binary, same hour, as described above.
  The oracle was rebuilt from `b444886` rather than trusted: the local baseline left over from an
  earlier tree predates `layerRoles`, and comparing against it produced 4615 differences that were
  all artefacts of its own staleness. The comparison is per-section and per-field rather than
  positional, because the `/v1/audit` window is a rolling 100 rows and any change in how many rows
  get written shifts every index; `signer_key_id` is excluded, since each build signs with its own
  key. The capture tooling is local release-audit equipment, not part of this repository.
- **The capability-token round trip driven against a real Postgres 16**, not only the Rust model of
  it. `tests/capability_token_pg_roundtrip.rs` simulates what `to_char` renders, which runs
  everywhere but had never been checked against the database it describes. With the release binary
  built `--features postgres` and pointed at a live server: migrations `1→9`, `expires_at` really
  `TIMESTAMPTZ`, and across 64 freshly minted tokens the rendering Postgres returns is
  byte-identical to the string that was signed, each with exactly six fractional digits. Mint →
  use → revoke end to end, revocation durable in the row, and a token minted before a restart still
  authorizing after it. Repeated with the database default `TimeZone` set to `Europe/Rome`, since
  `to_char` renders in the session zone while the format string hardcodes `+00:00`; the pool pins
  `SET TIME ZONE 'UTC'` on every connection and the round trip holds. That run is what surfaced the
  identity-persistence defect: before it was fixed, a token minted before the restart came back
  `404 agent_not_found`.
- **The ten `mongodb+srv://` cases replayed against binaries of both releases.** A `2.0.2` binary
  built from `b444886` answers `allow`/0 on nine of them and `review`/55 on the tenth
  (`trailing-noise`); this build answers `block`/80 on all ten. The corpus itself is local
  equipment, so the claim was re-driven from the ten context templates directly.
- The Bash Claude Code hook driven against a stub server reproducing each real status/body pair,
  because the defect lived entirely in how a JSON *error* body was told apart from a JSON *verdict*.
- The redirect refusal driven against a real hostile server issuing a real `302`.
- The open-mode startup warning observed firing on `0.0.0.0` and staying silent on `127.0.0.1` and
  on `0.0.0.0` without open mode.

## Prompt firewall audit boundary

The 20%-weighted `modules/injection_firewall/prompt_firewall.rs` is now audited. Stage 3 no longer
depends on an earlier signature/structure hit; full-width ASCII, mixed Latin/Cyrillic tokens,
case/tag-boundary variants and multiline download-to-shell payloads are covered. Signed summary
categories are deterministic, structural ratios count characters rather than UTF-8 bytes, and
ordinary `DAN` substrings, defensive security prose and inert HTML do not become false Block
evidence.

The Unicode treatment is deliberately bounded, not a claim of full confusable normalization: the
standard library maps full-width ASCII and the scanner catches practical mixed-script tokens. A
future product that accepts non-Latin identifiers as normal input should replace this with UTS #39
skeleton processing. The semantic stage remains a small directive-clause heuristic, not an NLP
classifier.

## Known gaps, stated rather than glossed

Carried over from 2.0.2 and still true: `iaga migrate` reads SQLite only, and so does
`iaga replay --export` (`main.rs:3079` — chain export and offline verification are unavailable on
Postgres); both hold for every shipped artefact, because `postgres` is not a default feature.
`POST /v1/nhi/challenge` does not persist on Postgres. `RUSTSEC-2026-0217` is still ignored in
`.cargo/audit.toml`. Dictum still cannot match on destination keys. And
`ghcr.io/iaga-team/iaga-sentinel` does not resolve — the image is not published.

New in this release and worth naming: `POST /v1/inspect` still returns the caller's own
`workspacePolicy`, thresholds included. The admin guard added here restricts **cross-workspace**
reads; a caller reading back the policy it was just governed by is unchanged, and the receipt wire
format depends on that field.

Four more, none of them new but all of them things a reader is entitled to know before deploying:

- **PostgreSQL is a compile-time feature and the shipped `Dockerfile` does not enable it.** The
  chart's own headline install turns Postgres on, yet an image built from this repository as-is
  exits 1 on a `postgres://` URL — after printing the whole "server is up" banner, so in a cluster
  the only symptom is a `CrashLoopBackOff`. Build with `--features postgres`, or stay on SQLite.
  The `Dockerfile` is deliberately unchanged here: flipping the default is a deployment decision,
  not an audit finding.
- **The stdio MCP planes carry no identity binding.** `iaga mcp-server` and `iaga proxy` present no
  API key, so the `agentId` they submit is asserted, not enforced, and any local caller can get a
  signed receipt under any agent id. Inherent to stdio, which has no transport to authenticate on.
  The 2.1.0 binding is an HTTP-layer control and `AGENTS.md` §8 now says so where it makes the claim.
- **`iaga-verify chain.json` without `--key` proves internal consistency, not authorship.** It falls
  back to the key embedded in the export — which a forger who re-signed the chain supplied too. It
  warns on stderr and stamps `key=embedded`, and this is ADR 0015's design, but the README's own
  example omitted the flag. It now pins the key and explains why in one sentence.
- **The SSE payload is snake_case (`tool_name`, `risk_score`); the REST audit surface is camelCase.**
  The console reads both, so nothing is broken, but a client written against one shape will not read
  the other.

## A note on one fix that was wrong first

The `/v1/response/scan` fix initially retargeted the taint sink from `NetworkEgress` to a new
`ToolResponse` sink at `medium` severity, which is advisory. That removed the false positive it was
aimed at, passed every test in the suite, and **silently deleted the credential detection that
shared the sink**: measured against 2.0.2, every `.cred/*` case in the corpus — Anthropic, AWS and
OpenAI keys, bare and inside code fences, env dumps, JSON and log lines — went from `block`/80 to
`allow`/0.

Nothing in the test suite caught it, because the tests were written against the same mental model
as the fix. What caught it was diffing against a real 2.0.2 binary. That is the reason the
characterization corpus exists, and it is why the "Known gaps" section above names a file rather
than omitting it.
